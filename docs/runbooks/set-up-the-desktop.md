# Set up the owner's desktop VM

**Status:** draft. Written 2026-11-13 from the code in this change (tests offline only). Not run to the end. First run 2026-11-14: Xfce and xrdp could not be installed, because EPEL 10 has no Xfce group, no xrdp and no xorgxrdp (measured from its repository metadata), and the AlmaLinux 10 base repositories have no xrdp. The role now uses GNOME and `gnome-remote-desktop`, whose package ships a system (headless) service, all from the base repositories. That the system service shows the GDM login over RDP on this VM is untested until the first run below.

**Isolation, by default (pick 219).** The agents configure the VM once and then keep no way in. The role removes the admin SSH key at the end of its first run, so later changes are a rebuild from teardown. The agents' Proxmox token holds AgentDev on `/pool/desktop` only while `DESKTOP_ACCESS` is on in `agent-access.sh` (the steps below), so after the build no agent can add a cloud-init key, reboot the VM or clone its disk. While the switch is off, the token keeps one line on VM 400 itself, the VM `DESKTOP_POWER_VMID` names: role `AgentDesktopPower`, `VM.Audit` and `VM.PowerMgmt` only, so it can see the desktop and turn it off and an unused desktop can't block a dev rebuild (the owner's words of 2026-11-17 23:58 UTC), and nothing more. The second identity, `agentlab@pve`, is kept out by NoAccess on every desktop VM, whatever the switch says. firewalld accepts 3389 only from the tailnet connector's address, where the owner's RDP arrives from (see "Where RDP comes from"). The owner sets the login and RDP passwords at the Proxmox console, so they pass through no agent.

The owner asked for a desktop in the lab, to sign in over RDP or VNC and log in to apps by hand (2026-11-13 05:04 UTC). It is a separate VM so what the owner types never sits beside the agents' keys.

**Where RDP comes from.** The owner picked "Your tailnet devices, anywhere" on a card on 2026-11-14 at 02:35:11 UTC, which replaced the owner's earlier "Home network only" pick of 02:20 UTC (that one would have needed a home-router route to the dev range and the Tailscale client off on the Mac). So RDP works from any of the owner's tailnet devices, at home or away, with no router or OPNsense change: the Mac reaches the dev range through the tailnet connector (CT 900), which advertises the lab ranges and rewrites the source of subnet traffic to its own address on the mgmt VLAN (SNAT stays on, the vendor default; see [Install the tailnet client in CT 900](set-up-tailnet-client-in-ct-900.md)). So the VM sees RDP arrive from the connector, not from the Mac, and `desktop_rdp_source` is the connector's address, set in the private inventory only. OPNsense already passes the mgmt VLAN to every lab VLAN, so this path needs no new firewall rule. Two limits: any device the tailnet policy lets reach the dev range can open 3389 (narrowing it to the owner's device is a tailnet policy change, not made), and the agents' cloud sessions receive no dev route, so they cannot reach the desktop over the tailnet (measured from a cloud session, 2026-11-14).

## Steps

1. Give the agents rights on the pool for this run: a PR that sets `DESKTOP_ACCESS=on` in `agent-access.sh` merges, then the owner (or the Mac lane on the owner's go) runs `proxmox-agent-access.sh run`.
   why: the owner picked "No rights after build" (pick 219), so the agents hold none between runs.
   expect: `agent-access: done (node <node>, desktop access on)`.

2. Plan the VM from a session on the box: `desktop plan`.
   expect: `1 to add`: one VM, ID in 400-499, bridge `dev`, in pool `desktop`.

3. Apply it: `desktop apply`, then set up the VM: `desktop configure`.
   expect: `failed=0`; the VM answers on SSH as the admin user until the role removes its key at the end of the run. Role `k8s_node_trust` runs first and puts the lab root (the last certificate of the box's `/etc/agent-keys/prod/lab-ca/c1-intermediate-chain.crt`) in `/etc/pki/ca-trust/source/anchors/`, so the desktop opens the apps' names with no certificate warning. `configure` stops first with "the desktop would not trust the lab's names" if that file is missing on the box. Before the role removes the admin key, it checks the trust it just set, and the run fails there if a check fails (`roles/desktop/tasks/trust_check.yml`, script `files/desktop-trust-check.sh`): the VM's extracted system store (`/etc/pki/tls/certs/ca-bundle.crt`, what curl reads) must verify the lab chain, which needs the lab root as its anchor, and each name in `desktop_trust_check_names` must open over https with that store and no `-k`. The run prints one line per check, such as `desktop trust: the system store verifies the lab chain (CN = Home Lab c1 Intermediate CA)`, and ends `desktop trust: every check passed`. The names are each app's short name, `<app>.<zone>` for grafana, argocd, sso, jellyfin and ntfy (the gateway name check's apps, [set-up-short-app-names.md](set-up-short-app-names.md)), opened only when `desktop_trust_check_reach` is true. It is false today, because the dev VLAN's firewall rules (role `opnsense_lab`: block the home LAN, ping and DNS to the firewall, then everything outside RFC 1918) pass nothing to prod, so the desktop has no route to the c1 Gateway on 443 and every name would fail as not reached. The pass is a firewall change on the owner's tap (D-0036 rule 8, [set-up-lab-network-and-firewall.md](set-up-lab-network-and-firewall.md)); once it is applied and the box's curl to a name answers, a one-line pull request sets it true, and from then on the run also proves that the desktop resolves the lab's names and reaches them. Until then the names' certificates are proven from inside c1 by the gateway's name check, and the desktop's browser cannot open the apps. The wrapper reads the zone from `k8s_gateway_zone` in the prod inventory it already holds (`/etc/agent-keys/prod/inventory-hosts.yml`, the file `c1-ansible` reads) and never prints it; `configure` stops first if that file is missing or holds no single plain zone. A name line reads `desktop trust: grafana.<zone>: 302, certificate verified`. Whether Firefox reads the same system store is not measured.

4. Take the rights away again: a PR that sets `DESKTOP_ACCESS=off` merges, then `proxmox-agent-access.sh run`.
   why: no agent keeps a way into the VM where the owner will type passwords.
   expect: `agent-access: done (node <node>, desktop access off)`; `pveum acl list` shows no AgentDev entry for `/pool/desktop`. The script sets `AgentDesktopPower` (`VM.Audit` and `VM.PowerMgmt`) for the dev token on VM 400 (`DESKTOP_POWER_VMID`), after removing any NoAccess line there, and checks with `pveum` that the token holds `VM.PowerMgmt` and nothing that opens, changes, copies or destroys the VM; it stops if not. If `agentlab@pve` exists, the script sets NoAccess for it and its token on every desktop VM (found from the pool's members), checks with `pveum` that the token holds no privilege there, and stops if it does. That ACL drops when the VM is destroyed, so run the script again after every `desktop apply`, not only at the end.

5. The owner opens the VM's console in Proxmox (VM, Console). It asks for two different passwords, each typed twice: the login password for `owner`, then the RDP password. No one else sees them, and neither is on a command line or in a log.
   expect: the prompt returns to a login; `/var/lib/desktop/password-set` exists and the remote desktop starts. The RDP client asks for `owner` and the RDP password, then GDM's login screen asks for the login password. The RDP password is stored on the VM's disk (there is no TPM), so a copy of it is in the VM's backups; it opens only the RDP layer, which is why it must differ from the login password, and GDM still asks for the login password.

6. Give the VM a name the owner's devices resolve, so the RDP client needs no address. In the private inventory, add `{ hostname: <desktop-name>, address: <the VM's address>, description: "Owner's desktop VM (RDP)" }` to `opnsense_lab_host_overrides` (`hosts.example.yml` shows the line), run the OPNsense playbook with tag `dns` (`ansible-playbook -i inventories/home/ playbooks/opnsense.yml --tags dns`), and add `<desktop-name>` to `split_dns_names` in the private `home/tailnet` tfvars and apply that folder (the default list holds no desktop name, because lab hostnames stay out of this public repository). Changing the tailnet is the owner's decision, so it waits for the owner's words naming the change.
   why: the owner's devices ask the lab's DNS only for the names in `split_dns_names` (pick 161); a name outside it resolves publicly, where the VM's private address is not published.
   expect: from a tailnet device, `<desktop-name>.<zone>` answers with the VM's address (`dig +short <desktop-name>.<zone> @100.100.100.100`).

7. The owner connects with an RDP client to the VM's name (or its address), port 3389, as user `owner`, over the tailnet (the owner's device on the tailnet, with the tailnet connector's route to the dev range on).
   expect: the RDP login, then GDM's login screen, then a GNOME session. Untested until the first run.

**gdm and the console prompt share tty1.** The prompt's service takes tty1 in place of the getty (`TTYPath=/dev/tty1`, `Conflicts=` and `Before=getty@tty1.service`), and gdm's greeter takes vt1. The prompt's `ExecStartPost` starts gdm, not the getty (gdm conflicts with getty@tty1, so a getty start would cancel gdm's queued start; reviewer, #795). The role writes a gdm drop-in, `After=desktop-set-password.service`, and starts gdm without waiting: on the owner's build gdm queues behind the prompt until the owner has typed the passwords, and on a test build the prompt is skipped and gdm starts at once. The system RDP daemon waits for gdm (measured 2026-11-20: gdm inactive, the daemon stuck "activating", `rdp-check` refused until a reboot started gdm), so the RDP service comes up without a reboot. Written, not run on a VM at the time of writing; the first test build after it is the run.

## Prove RDP from the agent box (test build)

Why: RDP stays off until the owner types both passwords at the console, and firewalld takes 3389 from the connector only, so before this nothing on the box could ever see the service answer (the 2026-11-19 rebuild never did). A test build lets the box prove it, then the owner's build replaces it.

1. VM 400 must be running (it is stopped whenever a dev rebuild needs the memory): `desktop status`, then `desktop start`. `start` refuses unless the node has the VM's memory plus 512 MiB available.
2. `desktop configure-test` instead of `desktop configure` on a fresh VM (same steps 1 to 3 above, rights on and off around the apply). The box makes two different random passwords, keeps them in `/etc/agent-keys/desktop-test-login` (0600, the keys user's, never printed), and the role runs the real console prompt unit with them fed on standard input (a test-only drop-in, `/run/desktop-test-passwords`, removed by the unit) instead of typed on tty1, so the prompt's script, its marker, the RDP daemon's start and its `ExecStartPost` all run as on the owner's build; firewalld also accepts 3389 from the box's own address.
3. `desktop rdp-check`: opens 3389, sends the X.224 connection request, reads the server's protocol choice, and does the TLS handshake. It sends no password at this step. expect: `the server picked CredSSP (NLA)` (or TLS), `TLS handshake done`, and `RDP service answers` (with `; no login was tried` on a build that is not a test build). On a test build it then runs a real network-level login with `xfreerdp +auth-only` as `owner` and the box-made RDP password, which reaches `xfreerdp` on stdin and is never printed. expect: `login PASS (NLA accepted the box-made test login; no GDM session was opened)`. A refusal prints `login FAIL (xfreerdp exit N)` and the command stops.

3b. `desktop diag` (test builds only) shows the remote desktop's unit state, journal, listening ports and firewall, over the admin key that a test build keeps (`desktop_lock_admin` false, ssh open; it needs the test login file, so it refuses on the owner's build). Use it when `rdp-check` fails.
4. `desktop stop` right after the check. The test VM must not hold 4096 MiB against a dev rebuild (the timer's rebuild keeps a running desktop and refuses when memory is short). It asks the VM to shut down; `desktop status` shows `stopped`.

The box's copy of the test passwords, `/etc/agent-keys/desktop-test-login`, is deleted by `desktop destroy`, and a plain `desktop configure` refuses while it exists, so a test-built VM can never become the owner's desktop and no test build leaves a credential on the box.

`grdctl --system rdp set-credentials <user>` with no password argument reads the password from standard input: in GNOME's `src/grd-ctl.c` (main branch, read 2026-11-20) `rdp_set_credentials` calls `prompt_for_input`, which reads one line from `STDIN_FILENO` and changes the terminal only when it is a tty. That is the source on main, not the version on AlmaLinux 10, so the first test build is where it is seen working.

Not proven by this (not done): that GDM then shows a session. `+auth-only` stops after the login is accepted. The box gets its RDP client from the `freerdp` package (AlmaLinux 10 AppStream, 3.32.2 listed by `dnf` on the box 2026-11-20), installed by the `agent_box` role.

The test build holds a credential the agents know, which the owner's desktop must not. After the check, run `desktop destroy`, `desktop apply`, then plain `desktop configure` so the owner types their own passwords at the console.

## If it fails

- `configure` stops with "REMOTE HOST IDENTIFICATION HAS CHANGED": the VM at the desktop's address has a new host key that `desktop destroy` did not clear (the VM was removed some other way, or the destroy ran before this was added). Run `desktop destroy`, then `plan`, `apply` and `configure`: the destroy drops that address's line from the box's `known_hosts`, and the new VM's key is accepted on first contact.
- `dnf` cannot find a package: the AlmaLinux 10 package set changed. The task `desktop | The desktop packages` names the step.
- The run stops at `desktop | Every trust check passed`: the line above it names the check. "does not verify the lab chain" means the lab root is not in the extracted store (role `k8s_node_trust` and its `update-ca-trust extract` handler); "TLS failed" means a name's certificate does not chain to the store; "not reached" means the VM has no route to prod's port 443 or no DNS answer for that name (curl exit 6 is DNS, 7 or 28 the route). The admin key is still in place, so fix the cause and run `desktop configure` again.
- The console shows a login prompt and never asks for the password: `desktop-set-password.service` did not run (the marker exists already, or getty took tty1). Check `systemctl status desktop-set-password` from the console as root, which is locked; rebuild the VM from teardown instead.
- The RDP client is refused: the owner has not set the password yet (the remote desktop waits for the marker), or the address the VM sees is not `desktop_rdp_source` (the connector's address, not the owner's device).
- The RDP client connects and drops, or shows no login screen: the system remote desktop daemon or GDM. Check `journalctl -u gnome-remote-desktop -u gdm` on the VM (from the Proxmox console, as the owner).

## Exit

the same order: access on, `desktop destroy` (tofu destroy with this folder's state), access off. The VM holds nothing the rest of the lab needs.
