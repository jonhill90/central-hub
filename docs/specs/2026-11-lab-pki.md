# Give the home lab its own certificate authority that survives rebuilds

## What and why

On 2026-11-08 at 07:08 UTC the owner asked for a PKI that works after a rebuild, with its root trusted on the owner's Mac, and for Proxmox and every hosted app to use it. [D-0028](../decisions/0028-run-a-lab-ca-with-the-root-off-cluster-and-one-intermediate-per-cluster.md) sets the shape: a root made once off every cluster, one intermediate per cluster restored into cert-manager on each rebuild. This spec is the work to build it. It serves PRD goal 4 (every piece can be replaced) and goal 6 (everything controllable from this repo). It crosses systems (the owner's Mac, the private store, c1, Proxmox and OPNsense), so it gets a spec (D-0007 rule 2).

Parts, in order:

1. **Root and c1 intermediate**, made by hand: [Create the lab root CA](../runbooks/create-lab-root-ca.md).
2. **Mac trust**: [Trust the lab root CA on a Mac](../runbooks/trust-lab-root-ca-on-mac.md).
3. **Restore into c1**: the intermediate goes from the private store into the Secret `lab-ca` in namespace `cert-manager`: [Restore c1's intermediate CA](../runbooks/restore-c1-intermediate-ca.md). This step is the one every rebuild repeats.
4. **Issuer as code**: the Ansible role `k8s_certs`, tag `labca` (`k8s_certs_lab_ca: true`), restores the Secret `lab-ca` from two files on the controller and makes the ClusterIssuer `lab-ca`. It moves to Argo CD with the rest of cert-manager.
5. **Gateway certificate**: the Gateway's certificate for `*.apps.c1.prod.<zone>` moves from the Let's Encrypt issuer to `lab-ca`.
6. **Proxmox and OPNsense**: a Certificate per host from `lab-ca`, copied by Ansible to each host's web UI and reloaded there. Each host also trusts the root.

### Lifetimes (agent pick, from the owner's earlier lab notes)

| Certificate | Key | Lifetime | Renewed |
|---|---|---|---|
| Root | ECDSA P-384 | 10 years | by hand, by making a new root before the old one ends; devices trust both for the overlap |
| c1 intermediate | ECDSA P-384, path length 0 | 5 years | by hand, a year before expiry, with the root runbook |
| Leaf (apps, hosts) | ECDSA P-256 | 90 days | by cert-manager, 30 days before expiry |

## Out of scope

- An ACME server (step-ca) for devices to order their own certificates; D-0028 names it as the exit path.
- Trust on devices other than the owner's Mac.
- Name constraints on the intermediate (D-0028 "Not decided here").
- Where the root's private key is kept: the owner's open question. The runbooks name it only as "the root key's offline home".
- Certificates for workloads talking to each other with mTLS.

## Acceptance criteria

### Automated

- [ ] `openssl verify -CAfile root.crt c1-intermediate.crt` on the owner's Mac: `OK`.
- [ ] `kubectl get clusterissuer lab-ca`: `Ready True`.
- [ ] `kubectl -n gateway get certificate apps`: `Ready True`, issuer `lab-ca`.
- [ ] `openssl s_client` against the Gateway's HTTPS listener shows a chain of leaf, c1 intermediate, and the lab root.
- [ ] Rebuild test: after the `lab-ca` Secret and ClusterIssuer are deleted and restored by the restore runbook, a newly issued leaf chains to the same root fingerprint as before.
- [ ] A second run of every playbook involved reports `changed=0`.
- [ ] The docs check passes, and a search of the diff finds no private key, real hostname, domain, single address or token.

### Manual (what the owner checks)

- [ ] The owner opens a c1 app, the Proxmox web UI and the OPNsense web UI in a browser on the Mac and sees no certificate warning.
- [ ] The owner can say where the root key and the intermediate key are kept, and how to put the intermediate back after a rebuild.
- [ ] The owner can say how to swap the issuer without touching the Mac (D-0028 rule 8).
